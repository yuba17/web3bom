# Pipeline Dashboard Integration — Scope Intake, Finding Queue, Real-Time Gates

**Date**: 2026-03-24
**Status**: Approved (rev2 — post-review fixes)
**Author**: Claude + User

## Overview

Three additions to the autonomous hunt system:

1. **Scope Intake** (`scope_intake.py`) — Feed repo + bounty text → auto-generate everything, start hunting
2. **Finding Queue** — Variant hunt and cross-component findings auto-enter pipeline via `finding_queue` in `current_hunt.json`
3. **Dashboard + Gates** — Real-time gate progress in the web UI via JSON cache written by `pipeline_gate.py`

Plus one cross-cutting change:

4. **PoC Fork Gate** — All PoCs must use `vm.createFork`/`vm.selectFork`. Mock-only PoCs are rejected by the `poc` gate.

---

## 1. Scope Intake (`audit-agents/scope_intake.py`)

### Purpose

Eliminate manual setup. User provides a cloned repo + bounty rules as text → system generates `current_hunt.json`, fichas, context files, and sets `current_component` to highest-LOC component.

### Interface

```bash
python3 audit-agents/scope_intake.py \
  --repo /path/to/cloned-repo \
  --platform cantina \
  --scope-text "Paste bounty rules here..."

# Or from a file:
python3 audit-agents/scope_intake.py \
  --repo /path/to/cloned-repo \
  --platform cantina \
  --scope-file /tmp/bounty-rules.txt

# Preview without writing:
python3 audit-agents/scope_intake.py \
  --repo /path/to/cloned-repo \
  --platform cantina \
  --scope-file /tmp/bounty-rules.txt \
  --dry-run
```

### Internal Steps

1. **Parse bounty text** — Extract via regex/heuristics:
   - Payouts by severity (`$XXK`, `$X.XM` patterns)
   - Exclusions (`out of scope`, `not eligible`, `known issues`)
   - Commit hashes / tags in scope
   - Contract names / file paths mentioned
   - Prior audits mentioned
   - Key attack surfaces / focus areas

2. **Map components** — Import `generate_component_map()` from `run_hunt.py` (no duplication):
   - Scan `src/` and `contracts/` for `.sol` files
   - Filter out tests, interfaces, libraries, mocks
   - Count LOC (excluding comments/blanks)
   - Detect imports/dependencies between contracts
   - If scope text mentions specific contracts → mark as `scope: "direct"`, others as `scope: "indirect"`
   - **Known limitation**: Only supports `.sol` files. Vyper/Cairo/Rust repos need manual mapping.

3. **Sort by LOC descending** — Largest component = priority 1

4. **Generate `current_hunt.json`**:
   ```json
   {
     "protocol": "<derived from repo name>",
     "repo_path": "/path/to/cloned-repo",
     "platform": "cantina",
     "payout": "<extracted or empty>",
     "status": "active",
     "current_component": "<highest LOC component>",
     "components_done": [],
     "components_remaining": ["<all components sorted by LOC>"],
     "component_map": [
       {
         "name": "ComponentName",
         "file": "src/ComponentName.sol",
         "loc": 422,
         "priority": 1,
         "status": "pending",
         "scope": "direct",
         "description": "<auto-generated from contract analysis>",
         "depends_on": ["OtherContract"]
       }
     ],
     "findings": [],
     "finding_queue": [],
     "scope_notes": {
       "prior_audits": "<extracted>",
       "exclusions": ["<extracted>"],
       "key_attack_surfaces": ["<extracted>"],
       "raw_scope_text": "<original text for reference>"
     },
     "last_session": "<ISO timestamp>"
   }
   ```

5. **Generate empty fichas** — One per component in `hunt_session/fichas/{protocol}/`

6. **Run `run_hunt.py --component X`** for the first component — Generates context + hunter prompts

7. **Run `pipeline_gate.py --component X --gate scope`** — Verify setup is valid

### Write-Order Contract

`scope_intake.py` writes `current_hunt.json` FIRST with all fields. Then `run_hunt.py --component X` is called and may only update: `current_component` and context/prompt files. It MUST NOT overwrite `component_map`, `findings`, `finding_queue`, or `scope_notes`.

### Robustness Rules

- If regex can't extract payouts → leave empty, print WARNING (don't guess)
- If regex can't extract exclusions → leave empty, print WARNING
- Always save `raw_scope_text` so the user can verify what was parsed
- If `current_hunt.json` already exists → abort with error (use `--force` to overwrite)
- `--dry-run` prints what would be generated without writing any files
- Print summary at end: "N components mapped, starting with X (Y LOC). Payouts: Z. Exclusions: N."

### Dependencies

- Imports `generate_component_map()` from `run_hunt.py` (mandatory — no duplication)
- Writes to `~/.claude/MEMORY/STATE/current_hunt.json`
- Creates `hunt_session/fichas/{protocol}/` directory

## 2. Finding Queue

### Purpose

When variant hunt or cross-component hunt discovers new potential findings, they enter a queue that tracks them through the full finding pipeline. No findings get lost between sessions.

### Data Structure

New field `finding_queue` in `current_hunt.json`:

```json
{
  "finding_queue": [
    {
      "id": "PL-M-01-V1",
      "title": "Same missing upper bound on preLIF2 in PreLiquidationFactory",
      "source": "variant",
      "parent_finding": "PL-M-01",
      "component": "PreLiquidationFactory",
      "severity_estimate": "low",
      "status": "pending_pipeline",
      "added_at": "2026-03-24T10:30:00Z",
      "notes": "Same root cause: missing bound check on constructor param"
    }
  ]
}
```

### Migration

If `current_hunt.json` exists but has no `finding_queue` field, all tools (`pipeline_gate.py`, `serve.py`) treat it as `[]`. The `--queue-finding` command creates the field automatically on first use.

### Sources That Write to Queue

| Source | `source` field | Extra fields |
|--------|---------------|--------------|
| Variant hunt | `"variant"` | `parent_finding: "<ID>"` |
| Cross-component hunt | `"cross-component"` | `components: ["A", "B"]` |
| Hunter analysis (finding in other component) | `"hunter_spillover"` | `discovered_by: "MathHunter"` |

### ID Auto-Generation

IDs are derived from parent finding: `{parent_id}-V{N}` where N auto-increments by scanning existing IDs in the queue.

- `PL-M-01` → variants: `PL-M-01-V1`, `PL-M-01-V2`, ...
- Cross-component (no parent): `XC-{A}-{B}-{N}` with component names in **alphabetical order** to avoid `XC-Vault-Gauge-01` vs `XC-Gauge-Vault-01` collisions. E.g. `XC-Gauge-Vault-01`.
- Hunter spillover: `{hunter_prefix}-{component}-{N}` e.g. `MATH-Factory-01`

### Status Lifecycle

```
pending_pipeline → in_pipeline → completed → moved_to_findings
                                           → dismissed (with dismissed_reason)
```

- `pending_pipeline`: Just discovered, waiting to start the finding pipeline
- `in_pipeline`: Actively going through PoC → Escalation → Variant → RedTeam → etc.
- `completed`: All finding gates passed
- `moved_to_findings`: Promoted to `findings[]` array in current_hunt.json
- `dismissed`: Investigated but not valid. Field `dismissed_reason` records why (false positive, duplicate, by-design, etc.)

### CLI Interface

New flags in `pipeline_gate.py` (intentionally in the same script — single entrypoint for all pipeline operations):

```bash
# Add a finding to the queue (auto-generates ID)
python3 pipeline_gate.py --queue-finding \
  --source variant \
  --parent PL-M-01 \
  --title "Same bound check missing in Factory" \
  --component PreLiquidationFactory \
  --severity low \
  --notes "Same root cause"

# List the queue (tabular: ID | Status | Component | Severity | Title)
python3 pipeline_gate.py --list-queue

# Update queue item status
python3 pipeline_gate.py --queue-update PL-M-01-V1 --qstatus in_pipeline

# Dismiss with reason
python3 pipeline_gate.py --queue-update PL-M-01-V1 --qstatus dismissed --notes "duplicate of PL-M-01"

# Promote completed finding to findings[]
python3 pipeline_gate.py --queue-promote PL-M-01-V1
```

### Integration Points

- **Variant hunt**: After finding variants, calls `--queue-finding` for each
- **Cross-component hunt**: After EdgeHunter finds interaction bugs, calls `--queue-finding`
- **Pipeline autonomous mode**: At start of session, checks `finding_queue` for `pending_pipeline` items
- **`pipeline_gate.py --status`**: Shows queue count and pending items
- **Dashboard**: Displays queue as a dedicated section

## 3. Dashboard + Gates (Real-Time)

### Gate Status Cache

`pipeline_gate.py` writes a JSON cache every time it executes. No daemon, no polling — the cache updates naturally as the pipeline progresses.

**File**: `hunt_session/gate_status.json`

**Written by**: `pipeline_gate.py` — automatically at the end of every `--gate`, `--status`, or `--fgate` invocation.

**Scope of export**: Only exports gates for the component being checked (incremental update). Each invocation merges its results into the existing `gate_status.json`, so the file accumulates data across components over time. Finding gates are exported for the specific finding being checked.

**Format**:

```json
{
  "component_gates": {
    "PreLiquidation": {
      "scope":    {"state": "pass",    "detail": "OK: protocol = morpho-pre-liquidation"},
      "hunters":  {"state": "fail",    "detail": "MISSING: hyp_PreLiquidation_DoSHunter.yaml"},
      "deepdive": {"state": "fail",    "detail": "MISSING: hyp_PreLiquidation_DeepDiveHunter.yaml"},
      "merge":    {"state": "pending", "detail": "Not yet reached"},
      "compile":  {"state": "pass",    "detail": "OK: forge artifacts found, newest 3.9h ago"},
      "phase1":   {"state": "pass",    "detail": "OK: Foundry cache directory exists"},
      "phase2":   {"state": "pending", "detail": "Not yet reached"},
      "phase3":   {"state": "pending", "detail": "Not yet reached"},
      "phase4":   {"state": "skip",    "detail": "SKIP: No optimize_* functions"},
      "phase5":   {"state": "skip",    "detail": "SKIP: No pure math functions"},
      "progress": "5/10",
      "blocked_at": "hunters"
    }
  },
  "finding_gates": {
    "PL-M-01": {
      "title": "Missing upper bound on preLCF2...",
      "severity": "low",
      "poc":        {"state": "pass",    "detail": "OK: PoC referenced + uses fork"},
      "escalation": {"state": "fail",    "detail": "NO_ESCALATION"},
      "variant":    {"state": "pending", "detail": "Not yet reached"},
      "redteam":    {"state": "pass",    "detail": "OK: DO_NOT_REPORT"},
      "verify":     {"state": "pending", "detail": "Not yet reached"},
      "report":     {"state": "pass",    "detail": "OK: Report found"},
      "submit":     {"state": "pending", "detail": "Not yet reached"},
      "progress": "3/7",
      "blocked_at": "escalation"
    }
  },
  "finding_queue_summary": {
    "total": 2,
    "pending": 1,
    "in_pipeline": 1
  },
  "updated_at": "2026-03-24T10:30:00Z"
}
```

**Gate states**: `"pass"` (green), `"fail"` (red), `"pending"` (gray — not yet reached), `"skip"` (gray with checkmark — optional gate not required). This replaces the boolean `ok` to support the 4-state UI.

**Note**: `complete` (component) and `reportable` (finding) are meta-gates (all-previous-pass checks). They are NOT displayed as circles in the dashboard — they are implicit from the overall progress. The progress denominator excludes them: 10 component gates (scope→phase5), 7 finding gates (poc→submit).

### Changes to `pipeline_gate.py`

1. **Auto-export**: After every gate check (`--gate`, `--status`, `--fgate`), merge results into `gate_status.json`
2. **`--export-json`** flag: Runs all gates for specified component and writes cache (not "reads existing" — there is no stored per-gate state)
3. **`--queue-finding`** / `--list-queue` / `--queue-update` / `--queue-promote`: Finding queue CLI
4. **Helper function** `export_gate_status(component, repo)`: Runs all 10 gates for the specified component, collects results with 4-state mapping (`pass`/`fail`/`pending`/`skip`), merges into existing `gate_status.json`

### Changes to `serve.py`

1. **Read `gate_status.json`** from `{hunt_dir}/gate_status.json` (resolved via `--hunt-dir` parameter, same as fichas and hypotheses)
2. **Read `finding_queue`** from `current_hunt.json` (already loaded)
3. **Add to `/api/dashboard` response**:
   ```json
   {
     "gates": { ... },          // from gate_status.json
     "finding_queue": [ ... ],  // from current_hunt.json
     ...existing fields...
   }
   ```
4. **Deprecate `fuzzPhases()`**: The existing hardcoded function in `index.html` (returns Phase 2-5 as `done: false`) is replaced by gate data from `gate_status.json`. Remove the function and read from `gates.component_gates[component].phase1` through `phase5` instead.

### Changes to `index.html`

Three new UI sections:

#### 3a. Component Gate Progress Bar

For each component in the component map, show a row of 10 circles:

```
PreLiquidation  [●●○◌●●◌◌●●]  5/10  ⛔ hunters
                 S H D M C 1 2 3 4 5
```

- Green (●) = `"pass"` or `"skip"`
- Red (○) = `"fail"`
- Gray (◌) = `"pending"` (not yet reached)
- Click circle → tooltip with `detail` text
- Shows `blocked_at` label

Placed **inside each component card** in the existing component map grid. Replaces the existing `fuzzPhases()` display.

#### 3b. Finding Pipeline Gates

For each finding in `finding_gates` (from gate_status.json), show 7 circles:

```

                 P E V R C W S
```

- P=poc, E=escalation, V=variant, R=redteam, C=verify(code), W=report(writer), S=submit
- Same color scheme as component gates
- Only show for findings that have gate data (not for `pending_pipeline` queue items)
- Placed in a **new "Finding Pipeline" panel** below findings table

#### 3c. Finding Queue Panel

New section "Cola de Findings" with:
- Badge in header showing count of `pending_pipeline` + `in_pipeline` items
- Table: ID | Title | Source | Parent | Component | Severity | Status | Added
- Status badges: `pending_pipeline` (yellow), `in_pipeline` (blue), `completed` (green), `dismissed` (gray)
- `pending_pipeline` items show only their status badge (no pipeline circles — they haven't started yet)
- Placed between the findings table and the activity feed

## 4. PoC Fork Gate — All PoCs Must Use Fork

### Rationale

Mock-only PoCs produce false positives (4/6 findings in Revert Lend session were mock artifacts). Every PoC must run against a mainnet fork to be valid.

### Changes to `pipeline_gate.py` → `check_finding_poc()`

The existing `poc` gate checks that a PoC exists and references PASS. Add a new check:

1. **Find PoC Solidity file** (existing logic)
2. **NEW: Verify fork usage** — grep the PoC file for `vm.createFork` or `vm.selectFork` or `fork` in the test setup
3. **If no fork evidence** → gate FAILS with:
   ```
   NO_FORK_IN_POC: PoC file found but does not use vm.createFork/vm.selectFork
     PoCs must run against mainnet fork, not mocks (CLAUDE.md rule)
     Add: uint256 forkId = vm.createFork(vm.envString("RPC_URL"), blockNumber);
   ```
4. **Exception**: If `current_hunt.json` has `pre_launch: true` (protocol not deployed), skip fork check

### Changes to `CLAUDE.md`

Update the PoC-related sections:
- Finding pipeline step 6: "FOUNDRY FORK + POC — PoC DEBE usar `vm.createFork`, nunca solo mocks"
- Finding pipeline gate `poc`: "Verifica que existe PoC + usa fork + PASS"
